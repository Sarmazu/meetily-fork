# Коррекция GigaAM: интеграция через существующий продукт

## 1. Причина и полномочия

При подготовке Story 1.5 пользователь спросил, почему создаётся много внутренней логики вместо подключения модели адаптером. Аудит требований по исходникам показал готовые процессы записи, импорта, повторной транскрибации, сохранения и настройки; GigaAM-движки/пакеты добавлены, но не подключены к этим процессам. История 1.5 остановлена с частичными изменениями. Источник: [аудит](../specs/spec-gigaam-cpu/brownfield-audit.md).

Пользователь прямо поручил обновить проектные документы и артефакты BMAD последовательно, максимально используя существующие классы, методы и код. Это разрешение применить документальную коррекцию; продолжение кода в этот запрос не входит. Режим batch принят по поручению выполнить обновление и предыдущему разрешению формировать оставшиеся артефакты без поштучных подтверждений. Последовательность изменений документов сохранена. Отдельный PRD отсутствует по принятому решению: его роль для этой функции выполняет SPEC; новый PRD/UX не создаётся.

## 2. Влияние

- Один эпик и десять стабильных ID историй сохраняются. CAP-1/CAP-2, FR1–FR12, NFR1–NFR6, UX-DR1–3 и поведенческие гарантии AD-1–AD-6 не сокращаются.
- 1.1–1.4 имеют реализацию и компонентные evidence; их не выполнять заново. Существующие статусы review не превращать автоматически в done при правке документации.
- 1.5: небольшой адаптер готовых движков к существующему trait, фиксация параметров и минимальная защита файлов. Убирается обязательность отдельного SessionFactory и имитации процесса записи/сохранения в его тестах.
- 1.6–1.9: расширение текущих интерфейсов и обработчиков вместо новых сценариев. В каждой истории закреплены reuse/delta/не входит.
- 1.10: прежняя функциональная матрица Windows 4×3, сохранение/ошибки/offline и совместимость. Производительность не измеряется.
- Runtime, ABI экспорта, модели, схема БД, deployment/CI не меняются этой коррекцией. Старые review/verification сохраняются как история, не объявляются результатом новой проверки.

## 3. Выбранный путь

**Direct Adjustment.** Скорректировать способ реализации в текущем эпике. Документальная работа — низкая сложность; оставшаяся интеграция — средняя, основной риск в live start/stop и shared wrappers. Точных сроков или экономии в процентах нет: они не измерялись. Убираются отдельный слой фабрики и повторная подготовка уже проверенных моделей; native приёмка остаётся.

Уточнение повторным аудитом: в Parakeet есть обычная RNNT-ветка. Сохраняются специфичные ABI/log-mel/CTC/RNNT GigaAM по причинам в дополнительном аудите; общий транспорт и очистка текста подлежат объединению. Сохранение всех компонентов целиком больше не является решением. Сокращение MVP не требуется и пользователем не запрошено. Частичные правки 1.5 не откатываются документальной задачей: привести их к новому контракту при возобновлении разработки.

## 5. Передача в разработку

Классификация **Moderate**: PO/Architect обновляет уже существующие требования/архитектуру/истории, DEV затем исполняет их. Это роли workflow, а не поручение запустить дополнительные агентные сессии.

Порядок документации: аудит → SPEC → AD-1–AD-6 → эпик/истории → техническая 1.5 → readiness/context/tracker → проверка согласованности. Все эти обновления входят в текущий запрос.

Следующий шаг кода после согласования пользователем: `bmad-build` по обновлённой spec 1.5. Не возобновлять старого implementer по прежнему handoff. Сначала проверить частичный diff и восстановить согласованность mod/session; затем adapter, интерфейс 1.6, импорт 1.7, повторная транскрибация 1.8, запись 1.9, приёмка 1.10. Результат 1.5 не объявлять работоспособной пользовательской функцией.

Критерии готовой реализации: четыре FP32-модели выбираются/скачиваются в привычном UI и дают сохранённый текст во всех трёх сценариях на Windows CPU; snapshot/ошибки/отмена/защита файлов работают; Whisper/Parakeet сохранены. Новый код обоснован конкретным пробелом, а существующие операции и хранение переиспользуются.
